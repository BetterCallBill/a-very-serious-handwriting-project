## Interview questions and answers / 面试问答

### Q: Why separate EventService from the controller? / 为什么把 EventService 与控制器分开？

**Answer:** The service handles application operations such as finding, validating, creating, updating, and deleting events. The controller handles HTTP concerns and translates service outcomes into responses. This lets us check service behaviour directly without starting an HTTP server, while keeping response construction in the controller.

**参考回答：** 服务负责查找、验证、创建、更新和删除事件等应用操作。控制器负责 HTTP，并将服务结果转换成响应。这样可以直接验证服务行为，无需启动 HTTP 服务；响应构造仍由控制器负责。

### Q: What should Delete(Guid id) return for an existing, missing, or already deleted event? / 删除已有、不存在或已删除的事件时应返回什么？

**Answer:** It returns `true` when the matching event is removed and `false` when no match exists. After a successful deletion, repeating the lookup finds no event, so the second deletion returns `false`. Missing-event deletion must leave the collection unchanged, and deleting one event must preserve the others.

**参考回答：** 成功移除匹配事件时返回 `true`，找不到时返回 `false`。第一次删除成功后，再次查找得到 null，因此第二次返回 `false`。不存在的事件不应导致集合变化；删除一个事件也不应影响其他事件。

### Q: Does returning a newly created Event mean it has been stored? / 返回新建 Event 就代表已经存储了吗？

**Answer:** No. Creating an object, adding it to `_events`, and returning it are separate operations. The original Create submission returned an event without adding it to storage, so the caller saw success but a later GetById could not find it. Success requires storing the event exactly once before returning it.

**参考回答：** 不是。创建对象、加入 `_events` 和返回对象是三个不同操作。最初的 Create 实现只返回对象，没有加入存储，导致调用者看到成功，但后续 GetById 找不到事件。成功路径必须先存储一次，再返回结果。

### Q: How should Create validate and map an EventRequest? / Create 应如何验证和映射请求？

**Answer:** Validate the whole request before changing storage. If any field is invalid, return `(null, error)` and leave storage unchanged. For a valid request, generate an ID, trim title and location, copy the requested start time and capacity, add the event once, and return `(createdEvent, null)`. A valid title does not make a zero-capacity request valid.

**参考回答：** 修改存储前先完成整个请求的验证。任一字段无效时返回 `(null, error)`，存储保持不变。请求有效时生成 ID、去除标题和地点两端空白、复制开始时间和容量、存储一次，再返回 `(createdEvent, null)`。标题合法不能抵消容量为零的问题。

### Q: Why pass DateTimeOffset now instead of reading UtcNow inside validation? / 为什么传入 now，而不是在验证中读取 UtcNow？

**Answer:** An explicit time input makes boundary checks repeatable. Tests can fix `now` and verify that past or equal start times fail and future start times succeed. Reading the system clock instead ignores the caller's input and makes results depend on when the check runs. Compare instants: two values with different offsets can represent the same instant and must still fail the equality boundary.

**参考回答：** 显式时间输入让边界检查可重复。测试可以固定 `now`，验证过去或相等的开始时间被拒绝，未来时间被接受。改读系统时钟会忽略调用者传入的时间，并让结果依赖运行时刻。不同偏移量可能表示同一时刻；这种情况仍属于相等边界，应拒绝。

### Q: What do the named tuple results mean? / 命名元组返回值代表什么？

**Answer:** `(Event? CreatedEvent, string? Error)` is one return value with two named fields, each of which can be null. Create returns either an event with no error or an error with no event. Update also uses `(null, null)` for a missing event, `(null, error)` for invalid input on an existing event, and `(updatedEvent, null)` for success. The controller must interpret these agreed outcomes; the tuple itself does not enforce valid combinations.

**参考回答：** `(Event? CreatedEvent, string? Error)` 是一个包含两个命名字段的返回值，每个字段都可以为 null。Create 成功时返回事件，失败时返回错误。Update 还用 `(null, null)` 表示事件不存在，用 `(null, error)` 表示已有事件的输入无效，用 `(updatedEvent, null)` 表示成功。控制器按约定解释这些结果；元组类型本身不会限制字段组合。

### Q: Why must Update look up, validate, and only then mutate the event? / 为什么 Update 必须先查找、再验证、最后修改？

**Answer:** Looking up first preserves the existing missing-resource behaviour, including when the request is invalid. Once an event is found, all validation must pass before assigning any properties. `existingEvent` refers to the object already in the list, so changing its title changes stored data immediately. Returning an error later does not undo that change. A valid new title with invalid capacity must leave every original field unchanged.

**参考回答：** 先查找可以保持原有的资源不存在处理方式，即使请求本身无效也是如此。找到事件后，必须全部验证通过才能赋值。`existingEvent` 引用列表中的对象，修改标题会立即改变存储数据；之后返回错误不会撤销修改。新标题有效但容量无效时，所有原字段都必须保持不变。

### Q: What should a successful update preserve, and how would you verify it? / 更新成功后应保留什么，如何验证？

**Answer:** Preserve the event ID, collection count, other events, and the input request. Update only the editable fields, trimming title and location. Check that GetById and GetAll reflect the changes, repeated updates work, and a later rejected update leaves the last valid state intact. The recorded Update review passed 50 direct service assertions; it did not verify HTTP integration or concurrent access.

**参考回答：** 保留事件 ID、集合数量、其他事件和输入请求，只修改允许编辑的字段，并去除标题和地点两端空白。验证 GetById 与 GetAll 能看到更新、重复更新有效、后续失败的更新保留最后一次有效状态。当日 Update 审查通过 50 项直接服务断言，但未验证 HTTP 接入或并发访问。

### Q: Will a later GET find a POST-created event if each request uses a new EventService? / 每个请求使用新服务实例，后续 GET 能找到 POST 创建的事件吗？

**Answer:** Not when `_events` belongs to each service instance and there is no separate shared store. The new service has its own collection, so it cannot see an event added only to the previous instance. All CRUD actions need the intended shared store. Choosing a shared lifetime alone does not solve concurrent access, mutable returned references, or persistence across restarts.

**参考回答：** 如果 `_events` 属于各个服务实例，且没有独立的共享存储，就找不到。新实例有自己的集合，看不到只加入旧实例的事件。所有 CRUD 操作必须使用预期的同一存储。共享生命周期本身不能解决并发访问、返回可变引用或重启后数据丢失的问题。
